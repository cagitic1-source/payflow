# 0001. HTTP-метрики через middleware с обёрткой ResponseWriter

## Статус

Принято. Задача PAY-7.

## Контекст

У API не было метрик HTTP-запросов: по `/metrics` нельзя было понять, сколько
запросов приходит, как быстро они обслуживаются и сколько из них заканчивается
ошибкой. Нужны длительность и коды ответов по каждому маршруту и число
запросов в обработке.

Ограничения:

- Число серий должно быть конечным. Id платежа из пути и произвольный метод
  из запроса не должны попадать в метки.
- Код ответа знает только обработчик. net/http не даёт прочитать его из
  ResponseWriter после ответа.
- Паника в обработчике должна попасть в метрики как 500.

## Решение

Метрики пишет одно middleware `HTTPMetrics` поверх ServeMux, на весь API
(`internal/app/http/middleware/metrics.go`):

- `payflow_http_request_duration_seconds{method,route,code}` - гистограмма
  длительности, бакеты от 0,5 мс до 2,5 с. Отдельного счётчика запросов нет:
  его заменяет `_count` гистограммы.
- `payflow_http_requests_in_flight` - запросы в обработке.

`route` - шаблон маршрута из ServeMux (`r.Pattern` без метода), например
`/v1/payments/{id}`. Запрос без маршрута получает `unmatched`. `method` -
один из стандартных методов, остальные сводятся к `other`.

Код ответа узнаём, оборачивая ResponseWriter. Обёртка `responseWrite`
запоминает первый `WriteHeader` (или 200 при первом `Write`) и отдаёт
исходный writer через `Unwrap`, чтобы работал `http.ResponseController`.

Метрики регистрируются в переданном `prometheus.Registerer`, а не в
глобальном реестре. `NewHTTPMetrics` возвращает ошибку регистрации, тесты
берут свой реестр.

Порядок цепочки в `router.New`, снаружи внутрь:
`RequestID -> HTTPMetrics -> Recover -> mux`.

- `HTTPMetrics` стоит внутри `RequestID`. ServeMux пишет шаблон в `r.Pattern`
  того запроса, который получил, а `RequestID` подменяет запрос через
  `r.WithContext`. Снаружи `RequestID` метрика видела бы только `unmatched`.
- `Recover` стоит внутри `HTTPMetrics`. Ответ 500 после паники проходит через
  обёртку метрики. Если ответ уже начат, `Recover` не дописывает 500, а
  обрывает соединение через `http.ErrAbortHandler`. `HTTPMetrics` видит, что
  обработчик не завершился, и пишет 500.

## Последствия

Плюсы:

- Серий конечное число: методы × маршруты × коды. Новые id их не добавляют.
- Паники видны в метриках как 500, в том числе обрыв уже начатого ответа.
- Обработчики маршрутов ничего не знают о метриках.

Минусы и ограничения:

- **Метрика зависит от `r.Pattern`.** Между `HTTPMetrics` и ServeMux нельзя
  ставить middleware, которые подменяют запрос, иначе все запросы станут
  `unmatched`. Это проверяет `TestRouter_RecordsHTTPMetrics`.

- **Обёртка прячет методы исходного ResponseWriter.** Экспортированные
  (`Flush`, `Hijack`, `SetWriteDeadline`) доступны через
  `http.ResponseController` благодаря `Unwrap`, но прямое приведение типа,
  например `w.(http.Flusher)`, уже не срабатывает. Неэкспортированные методы
  недоступны вовсе.

  Так сломался лимит тела запроса. `http.MaxBytesReader` сообщает серверу о
  превышении лимита через неэкспортированный метод `requestTooLarge` у
  исходного ResponseWriter. Проверяет он его приведением типа, без `Unwrap`.
  Обработчик `CreatePayment` ставил `MaxBytesReader` сам и после PAY-7
  получал уже обёртку. Лимит по-прежнему срабатывал, но сервер о нём не
  узнавал: он не закрывал соединение после ответа и вычитывал до 256 КиБ
  лишнего тела, чтобы переиспользовать соединение. Тесты на
  `httptest.NewRecorder` этого не видят: у рекордера `requestTooLarge` нет
  ни с обёрткой, ни без неё.

  Исправление: тело ограничивает `middleware.BodyLimit`, самый внешний в
  `router.New`, и ему достаётся исходный writer. Сквозной тест
  `TestAPI_BodyOverLimitClosesConnection` через настоящий сервер проверяет,
  что после превышения лимита приходит `Connection: close`.

  Правило на будущее: всё, чему нужен исходный ResponseWriter, ставится
  снаружи всех обёрток. Новая обёртка в цепочке - повод проверить, что под
  ней ничего такого нет.

- **Обёрток на запрос две.** Свою ставят и `HTTPMetrics`, и `Recover`, и
  каждая отдельно отслеживает начало ответа.

- **Обёртка видит не всё.** `WriteHeader` с кодом 1xx, например 103 Early
  Hints, она примет за итоговый код. `Flush` через `http.ResponseController`
  идёт мимо неё, и начало ответа она не заметит. Сейчас API не шлёт 1xx и
  ничего не стримит. Если начнёт, обёртку надо доработать.
